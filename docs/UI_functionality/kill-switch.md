# Вкладка «Kill-Switch»

Жёсткая блокировка трафика профиля при падении Xray — вместо риска уйти в
интернет напрямую в обход VPN.

## Как это устроено на самом деле (два уровня)

1. **Мягкий (всегда включён, бесплатно)**: трафик профиля перенаправляется
   на локальный инбаунд Xray правилами файрвола SmartRoute (`nftables`
   REDIRECT). Если процесс Xray упал — цели перенаправления нет, и
   соединение обрывается локально, а не тихо уходит напрямую. Это уже
   покрывает geosite-/custom-профили без какой-либо дополнительной
   настройки — то, что описано ниже, добавляет **явную, гарантированную**
   блокировку поверх этого.
2. **Жёсткий (по галочке, отдельно на каждый профиль)**: `dnsmasq`
   слушает DNS-запросы с LAN; когда клиент резолвит домен из списка
   профиля, IP-адрес автоматически добавляется в ipset (`sr_killswitch`).
   Правило файрвола блокирует (`REJECT`) весь LAN→WAN трафик на IP из
   этого ipset. Правило стоит **постоянно**, с момента включения галочки
   — не опрашивается раз в минуту на предмет "жив ли Xray" (так было
   раньше, оставляло до 60 секунд окно уязвимости). Корректно
   перенаправленный трафик (когда Xray жив) до этого правила вообще не
   доходит — DNAT на локальный адрес идёт через цепочку `INPUT`, не
   `FORWARD`, так что правило физически не мешает нормальной работе и
   срабатывает только в момент, когда перехват сломан (тот самый случай,
   для которого оно и существует).

## Таблица профилей

Одна галочка на каждый geosite-/custom-профиль. Для geosite-категорий —
пометка о неполном покрытии (см. ниже).

## Почему geosite не может дать 100% покрытия

Источник geosite (`v2fly/domain-list-community`, из него же собирается
`geosite.dat` для самого Xray) содержит четыре типа записей:

- `domain:` — точный домен + поддомены — **можно** зарезолвить заранее.
- `full:` — только точный домен — **можно**.
- `keyword:` — любой домен, содержащий подстроку — **нельзя**: это не
  домен, а правило сопоставления, доменов с такой подстрокой бесконечно
  много, большинство ещё не существует.
- `regexp:` — сопоставление по регулярке — **нельзя** по той же причине.

`dnsmasq` может реагировать только на реальные DNS-запросы к конкретным,
заранее известным именам. Xray сам сопоставляет `keyword:`/`regexp:` **в
моменте**, по живому SNI/Host запроса — а не через предварительный список.
Byte-in-byte повторить это через "зарезолвь домен → добавь IP в список"
нельзя в принципе — это архитектурный потолок метода, не недоработка.

`killswitch.sh` берёт из geosite-категории только `domain:`/`full:`
записи (`resolve_geosite_domains()`), `keyword:`/`regexp:` — пропускает.
Для категорий, которые сильно опираются на `keyword:`/`regexp:` (часто —
крупные сервисы с динамическими CDN-поддоменами), покрытие соответственно
неполное.

## Отдельный, независимый пробел: IP-диапазоны профиля не защищены

`ks_rebuild_dnsmasq()` смотрит только на `domain_source` профиля — **не**
на `ip_ranges`. Значит, у профиля вроде Telegram (где `ip_ranges` как раз
и нужен, потому что MTProto ходит по IP напрямую, без DNS) kill-switch
сейчас не даёт вообще никакой защиты для этой части: dnsmasq никогда не
увидит DNS-запрос для приложения, которое и так не резолвит домен —
ipset для этих IP просто никогда не заполнится.

## Как приблизиться к 100% (реально, не идеально)

1. **Добавить `ip_ranges` профиля в ipset напрямую** — IP уже известны
   буквально, резолвинг не нужен вообще. Закрывает пробел выше полностью,
   для таких профилей — 100% реально достижимо. Пока не реализовано.
2. **Добавить geoip-диапазоны крупных сервисов** (не домены, а целые
   IP-диапазоны — v2fly/Loyalsoldier поддерживают отдельные списки по
   сервисам, независимо от домена) в тот же ipset как CIDR. Ловит и
   `keyword:`/`regexp:`-случаи (обычно резолвятся в тот же диапазон), и
   DNS-over-HTTPS (домен зарезолвлен в обход dnsmasq, но IP всё равно в
   диапазоне), и IP-литералы. Работает только для сервисов с собственными
   выделенными диапазонами — не для всего, что сидит за общим CDN вроде
   Cloudflare (иначе заблокируется пол-интернета).
3. **Блокировать DNS-over-HTTPS/DoT** (мера для вкладки «Защита от
   утечек», не kill-switch напрямую) — иначе устройство может резолвить
   домен в обход dnsmasq вообще, IP никогда не попадёт в ipset.

Ни один из этих пунктов пока не реализован — это план, не факт. Истинные
100% (byte-for-byte как у Xray) недостижимы этим методом никогда в
принципе; пункты 1–2 закрывают подавляющее большинство реальных случаев.

## Инструкция по тестированию на реальном устройстве

Подготовка (на роутере по SSH):
```
ipset list sr_killswitch          # что реально сейчас заблокировано
```

### Тест 1 — базовый (должен проходить уже сейчас)

1. В UI включить kill-switch для профиля с geosite (например YouTube).
2. С реального устройства открыть сайт из этой категории — должен
   работать как обычно.
3. На роутере: `killall xray` (или кнопка «Стоп» на вкладке Статус).
4. С того же устройства попробовать открыть тот же сайт снова —
   **должно быть отказано в соединении**, не должно тихо уйти напрямую.
5. `xkeen -start` (или кнопка «Старт») — убедиться, что всё снова
   работает штатно.

### Тест 2 — дыра keyword/regexp (ожидаемо покажет утечку)

1. Найти конкретный домен из той же категории, который матчится по
   `keyword:`/`regexp:`, а не `domain:`/`full:` (зависит от конкретной
   категории — нужно смотреть исходный список).
2. Xray остановлен (как в тесте 1) → попробовать открыть именно этот
   домен → ожидаемо **должен пройти напрямую** (реальная утечка), в
   отличие от домена из основного списка в тесте 1.

### Тест 3 — дыра ip_ranges, профиль Telegram (ожидаемо покажет утечку)

1. Включить kill-switch для профиля с заданными `ip_ranges` (например
   Telegram).
2. Остановить Xray.
3. Открыть нативное приложение (не веб-версию) — ожидаемо сообщения
   продолжат доходить (утечка через MTProto, ipset пустой для этих IP —
   см. «Отдельный, независимый пробел» выше).
