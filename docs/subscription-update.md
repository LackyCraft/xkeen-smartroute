# Обновление подписки: как устроен импорт и маппинг тегов профилей

Описание механики обновления подписки — почему теги серверов вообще могут
меняться между обновлениями, как мы сопоставляем старые записи с новыми, и
что происходит с профилями, если сервер у провайдера пропал по-настоящему.

## Откуда вообще берётся тег сервера

При импорте (`sr_import()`, `lib/subscription.sh`) каждая строка подписки
(`vless://...`/`trojan://...`) превращается в тег вида:

```
sr_<label>_<host-слаг>_<port>_<имя-слаг>_<хеш-строки>
```

Уникальность тега гарантирует **хеш всей сырой строки целиком** (secret,
host, port, все query-параметры) — не читаемый слаг имени, он там только
для удобства чтения сгенерированного конфига глазами. Дошли до этого не
сразу — по пути нашли и закрыли три реальных источника коллизий тегов на
живой подписке:

1. `slugify()` заменяет **любой** не-ASCII символ на `_` и схлопывает
   подряд идущие — кириллическое имя целиком превращается в пустоту/один
   символ, что молча сливало разные по названию узлы в один тег.
2. Обрезание secret до первых 8 символов было недостаточным — у части
   узлов разные UUID совпадают именно в этих первых 8 символах.
3. Несколько узлов на одном host+port+secret с одинаковым отображаемым
   именем, отличающихся только XHTTP `path`/`host`/`sni` — не редкость,
   а обычная практика провайдеров (несколько CDN-граней перед одним
   бэкендом).

Хеш всей строки закрывает все три сразу: два тега могут совпасть только
если исходные строки byte-in-byte идентичны — а если идентичны, это и
есть один и тот же тег, это правильно.

## Почему тег может измениться при обновлении

Раз тег зависит от **всей** строки, любое изменение хоть одного
query-параметра у провайдера (ротация `sid`/`pbk`, смена `path`/`host` у
CDN, правка padding-настроек в `extra`) на следующем обновлении даст
**другой** тег для того же самого, с точки зрения провайдера, узла. Без
специальной обработки это молча рвёт связь: профиль, у которого этот
сервер был отмечен галочкой, просто перестаёт его "видеть" — тег в
`.servers`/`.fixed_server` профиля ссылается в никуда.

## match_key: как сопоставляем старое с новым

Проверенные и отклонённые варианты сопоставления:

- **По IP:port** — не годится. Один физический сервер держит десятки
  разных виртуальных узлов на одном host+port ("маркетинговые дубликаты"),
  сопоставление по IP:port схлопнуло бы их в один.
- **По имени** — тоже не годится (см. коллизии тегов выше: имена не
  уникальны, могут быть пустыми после транслитерации, провайдер может их
  вообще переименовать).

Вместо этого — **`match_key` = host + port + secret + камуфляж-домен**
(значение `sni`, а если его нет — сам `host`). Это ровно то сочетание,
которое реально идентифицирует "тот же узел" у провайдера: секрет отличает
разные виртуальные узлы на одном host+port, камуфляж-домен отличает разные
CDN-грани с одним и тем же секретом. Всё остальное (path, padding/xmux
настройки, alpn, fp, отображаемое имя) — то, что провайдер может
подправить у **того же** узла, не подразумевая замену, поэтому в ключ не
входит.

`match_key` считается для каждого сервера при импорте и хранится прямо в
`servers.json` рядом с тегом — не вычисляется заново задним числом.

## Что происходит в профилях

При каждом обновлении подписки (`sr_import()`) для затронутого
label'а:

1. **До** перезаписи `servers.json` снимается снимок старых записей этого
   label'а (тег + `match_key` + имя).
2. После того как новый список импортирован, `sr_remap_profile_tags()`
   (`lib/subscription.sh`) сравнивает: какие старые теги пропали из нового
   списка, и есть ли среди новых запись с тем же `match_key`.
3. Для каждого профиля (`lib/profiles/*.json`):
   - Тег **нашёлся** по `match_key` → тихо заменяется на новый, без следа
     — тот же узел, просто сменил адрес/параметры.
   - Тег **не нашёлся** → удаляется из активного пула профиля (`.servers`
     или `.fixed_server`), но не молча: попадает в
     `profile.removed_servers` (имя + время), вкладка «Профили» подсвечивает
     это красным предупреждением под строкой профиля.
4. `profile.removed_servers` **очищается автоматически**, как только
   профиль в следующий раз явно сохраняют через UI (обычное сохранение
   всегда пишет свежий `.servers` без поля `removed_servers`) — отдельной
   кнопки "принять к сведению" не нужно.

## Защита от "зависшего" fixed_server

Для `mode: "fixed"` профиля `removed_servers` **не обнуляет**
`fixed_server` — тег остаётся (уже нерабочий), чтобы UI мог показать, что
именно пропало. Это специально: если бы `genroute.sh` слепо генерировал
правило с несуществующим `outboundTag`, весь смёрженный конфиг Xray не
прошёл бы валидацию `xray run -test`, и `_sr_xray_validate()` (уже
существующий защитный механизм) отказался бы применять **вообще любые**
изменения маршрутизации — не только для этого профиля, а для всех, пока
кто-то не поправит руками.

Вместо этого `genroute.sh` теперь сам проверяет: существует ли
`fixed_server` профиля среди реально известных тегов, прежде чем
генерировать под него правило — если нет, профиль корректно пропускается
(как уже делает `sr_pick_top1` для balancer-режима), а не ломает валидацию
всего конфига.

## Переключатель автообновления

Настройка **«Автообновление подписок»** (вкладка «Профили») — по
умолчанию включено (существующие установки не меняют поведения).
Выключает только **плановый** путь (`sr_refresh_due`, вызывается из
cron) — явная кнопка «Обновить сейчас» на вкладке «Подписки» продолжает
работать всегда, это осознанное действие пользователя, а не то, о чём
предупреждение.

Хранится в `/etc/xkeen-smartroute/state/auto_refresh_enabled` (`1`/`0`),
CLI: `subscription.sh get-auto-refresh-enabled` /
`set-auto-refresh-enabled <true|false>`.
