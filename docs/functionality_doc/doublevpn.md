# Double VPN: релей всего трафика через один выбранный шлюз

Техническое описание фичи "Double VPN" — опциональный дополнительный хоп
перед всеми остальными outbound'ами. Мотивация (со слов пользователя, при
постановке задачи): провайдер часто блокирует отдельные сервера подписки
напрямую (см. также [balancer.md](balancer.md#сознательные-ограничения) про
таймауты и ложные "смерти"), но почти всегда оставляет доступным хотя бы
один сервер. Если весь остальной трафик — и обычный, и собственные
health-check пробы SmartRoute — пустить сначала через этот один всегда-
доступный сервер, блокировки конкретных destination-адресов со стороны
провайдера перестают иметь значение: провайдер видит только соединения к
одному IP шлюза.

## Механизм: `sockopt.dialerProxy`, не самодельный туннель

Xray-core умеет "цепочку outbound'ов" из коробки. Найдено и подтверждено
прямым чтением реального исходника (не по памяти, WebFetch на этот проект
регулярно даёт неточный пересказ вместо точного текста — см. `AGENTS.md`):
искомое поле — **не** `streamSettings.proxySettings` (структуру
`ProxyConfig{Tag, TransportLayerProxy}` из `infra/conf/transport_internet.go`
поначалу приняли за него, но `StreamConfig.Build()` в том же файле её нигде
не использует — мёртвый/legacy код), а `streamSettings.sockopt.dialerProxy` —
простая строка с тегом другого outbound'а
(`infra/conf/transport_sockopt.go`: `DialerProxy string
\`json:"dialerProxy"\``).

Рантайм-механика (`transport/internet/dialer.go`):

```go
if len(sockopt.DialerProxy) > 0 {
    obm := ...
    h := obm.GetHandler(sockopt.DialerProxy)
    return redirect(ctx, dest, sockopt.DialerProxy, h), nil
}
```

Когда outbound A пытается подключиться к своему настоящему адресу (`dest`),
и у A в `streamSettings.sockopt.dialerProxy` стоит тег outbound'а B — вместо
прямого TCP-коннекта запрос **перенаправляется через B**: B физически
устанавливает соединение до адреса A, а поверх уже накручивается собственный
протокол A (VLESS/REALITY/XHTTP). Итоговый путь трафика: роутер → B (шлюз) →
настоящий адрес A → интернет.

## Почему это автоматически работает и для Observatory

`redirect()` в `dialer.go` вызывается для **любого** дайла через outbound A —
не важно, реальный это пользовательский трафик или health-check-проба
Observatory (`app/observatory`, см. [balancer.md](balancer.md)). Обе идут
через один и тот же механизм диспетчеризации outbound'ов. Значит: как
только у A выставлен `dialerProxy`, Observatory, пингуя A, тоже автоматически
идёт через B — **без единой правки** `gateway/xray.go` или самого механизма
Observatory. Это ключевая причина, почему фичу можно было реализовать чисто
на уровне генерации конфига (`lib/genroute.sh`), не трогая ни gateway, ни
health-polling.

## Хранение состояния и выбор шлюза

`SR_DOUBLEVPN_FILE` = `/etc/xkeen-smartroute/state/doublevpn.json`:

```json
{"enabled": true, "servers": ["sr_...", "sr_...", ...]}
```

`servers` — пул кандидатов-шлюзов, выбранных пользователем (тот же
чекбокс-пикер, что и у профилей, сгруппированный по подписке). Из этого
пула на каждом regen выбирается **один** лучший тег — тем же самым
`sr_pick_top1` (`lib/genroute.sh`), что использует balancer-режим профиля:
свежий пинг + `health.json`, 4-уровневый тир (см.
[balancer.md](balancer.md#как-выбирается-топ-1-сервер-профиля-sr_pick_top1)).
Поскольку `sr_pick_top1` читает `.servers` из файла профиля, а не принимает
массив напрямую, пул на время вызова записывается во временный
profile-подобный файл (`$SR_STATE_DIR/.doublevpn_pool.json`) и удаляется
сразу после.

Результат каждого regen (какой шлюз выбран прямо сейчас, для UI) пишется в
`SR_DOUBLEVPN_CURRENT_FILE` = `state/doublevpn_current.json`:

```json
{"enabled": true, "gateway": "sr_...", "pool_size": 2}
```

`gateway: null` означает "включено, но в пуле сейчас нет ни одного
достижимого сервера" — в этом случае трафик остаётся прямым (см. ниже), а не
блокируется.

## Ремап тегов пула при обновлении подписки

Найден и исправлен реальный пробел: тег сервера зависит от содержимого его
собственной строки в подписке (см.
[subscription-import.md](subscription-import.md)) — стоит провайдеру
поменять хоть один query-параметр узла, тег меняется целиком, хотя физически
это тот же сервер. Для профилей это давно отрабатывает
`sr_remap_profile_tags` (`lib/subscription.sh`) — реассоциирует профиль на
новый тег через `match_key`, либо, если сервера действительно не стало,
переносит его в `.removed_servers`. **Пул Double VPN в эту логику изначально
не входил вообще** — `sr_apply_doublevpn` лишь молча отфильтровывал
несуществующие теги при выборе шлюза, сам список `.servers` не трогал.
Подтверждено вживую: пул из 27 сохранённых серверов после нескольких
обновлений подписки на 16 из них ссылался на уже несуществующие теги —
UI показывал их как «—»/«нет ответа» (`serverForTag()` не находит сервер,
откатывается на `{tag, name: tag}`), и они копились бесконечно, каждое
следующее обновление только добавляло новых.

Исправлено симметрично профилям: `_sr_compute_tag_remap` (вынесена как
общий хелпер, используется и `sr_remap_profile_tags`, и новой
`sr_remap_doublevpn_tags`) вычисляет diff старого/нового списка серверов
подписки один раз, обе функции применяют его каждая к своему хранилищу.
`sr_remap_doublevpn_tags` вызывается сразу после `sr_remap_profile_tags` на
каждом refresh (`lib/subscription.sh`, после замены `servers.json`):

- Тег, для которого нашёлся `match_key` в новом списке — заменяется на новый
  тег на месте в `.servers`, без потери позиции.
- Тег, для которого совпадения нет — удаляется из `.servers` и добавляется в
  `.removed_servers` (`{tag, name, removed_at}`), в том же формате, что и у
  профилей.
- `.removed_servers` копится (`existing + new`), не перезаписывается — как и
  у профилей, единственный способ его очистить — реально пересохранить пул
  через UI (`sr_set_doublevpn_servers` явно сбрасывает `.removed_servers = []`
  на каждое ручное сохранение, тем же принципом, что полная перезапись файла
  профиля через `save_profile` естественным образом теряет старое поле).

UI (LuCI и панель) показывает `removed_servers` красным предупреждением под
таблицей «Сейчас участвуют в Double VPN», тем же паттерном, что и у Профилей.

## `sr_apply_doublevpn`: как патчится outbounds-файл

Функция в `lib/genroute.sh`, вызывается из `sr_regen()` перед построением
routing-правил. В отличие от `05_routing.smartroute.json`/
`07_observatory.smartroute.json` (которые `sr_regen()` строит с нуля каждый
раз), `sr_apply_doublevpn` **патчит уже существующий**
`04_outbounds.smartroute.json` — файл, которым владеет `subscription.sh`
(пишет его целиком на каждый импорт/refresh). Патч — не toggle поверх
предыдущего состояния, а полный пересчёт "как должно быть сейчас" через
`jq map()`, поэтому идемпотентен и не нуждается в отдельном "чистом" бэкапе:
при выключенной фиче или при отсутствии живого шлюза `sockopt` просто
снимается со всех outbound'ов, при включённой — выставляется заново на
основе текущего содержимого файла, независимо от того, что там было до
этого.

```jq
.outbounds |= map(
  if (.tag as $t | $pool | index($t) != null) then
    .streamSettings |= (if type=="object" then del(.sockopt) else . end)
  else
    .streamSettings.sockopt = {dialerProxy: $gw}
  end
)
```

Небольшое окно рассинхронизации возможно, если subscription-refresh
перезапишет `04_outbounds.smartroute.json` между двумя запусками `regen`
(каждые 3 минуты по cron) — самоисправляется на следующем regen, ничего
руками чинить не нужно.

## Участники пула никогда не заворачиваются

Ни один сервер из пула шлюзов не получает `dialerProxy` — ни через самого
себя, ни через другого участника пула. Причина не только в очевидном риске
петли (шлюз, завёрнутый сам на себя): ранжирование `sr_pick_top1` для
**выбора** лучшего участника пула опирается на `ping.json`/`health.json`,
отражающие **прямую** достижимость каждого кандидата. Если бы участники пула
заворачивались друг через друга, это исказило бы именно тот сигнал, по
которому между ними выбирают.

## Триггер рестарта Xray

`sr_regen()` уже сравнивал старое/новое содержимое
`05_routing.smartroute.json` и `07_observatory.smartroute.json`, чтобы решить,
нужен ли рестарт. Патч outbounds-файла — третий независимый источник
изменений (шлюз может смениться, даже если ни один профиль и ни один
`subjectSelector` не поменялись), поэтому добавлена третья аналогичная
проверка (`outbounds_before`/`outbounds_after`, byte-for-byte) — рестарт
происходит, если изменился **любой** из трёх файлов, не только routing.

## Живой тест: подтверждённое восстановление связности

Проверено на реальном роутере, не только по форме конфига. Пул из двух
реально живых серверов подписки, шлюз выбран `sr_pick_top1` автоматически.
Для тега, который `health.json` на тот момент помечал мёртвым по таймауту
(прямой TCP/TLS до него не проходил), после включения Double VPN лог Xray
(изолированный тестовый процесс, тот же метод, что и в
[balancer.md](balancer.md#сознательные-ограничения) — отдельный `xray run
-confdir`, ничего боевого не трогает) показывает:

```
transport/internet: redirecting request tcp:<dead-server-ip>:<port> to sr_gussitrade_...
proxy/vless/outbound: tunneling request to tcp:<dead-server-ip>:<port> via <gateway-ip>:<gateway-port>
```

— то есть реальную маршрутизацию через шлюз, не просто наличие поля в
конфиге. Из трёх протестированных таким образом "мёртвых по таймауту" тегов
два ответили настоящим `HTTP 204` через цепочку (тот же `probeUrl`, что
использует сам Observatory) там, где напрямую они не отвечали вовсе — то
есть Double VPN реально восстанавливает связность для серверов, недоступных
напрямую. Третий тег через цепочку соединился (тот же `redirecting`/
`tunneling` в логе), но упал с `REALITY: received real certificate
(potential MITM or redirection)` — это отдельная, не связанная с блокировкой
провайдера проблема на стороне самого сервера-получателя (см.
[balancer.md](balancer.md#два-независимых-сигнала-пинг-и-observatory) про
эту же ошибку); цепочка не может исправить сломанный REALITY-сертификат на
destination, потому что REALITY-проверка идёт между клиентом и конечным
сервером напрямую, независимо от того, каким путём к нему шёл TCP-коннект.

## UI

Отдельная вкладка (не часть "Профили" — по явной просьбе пользователя
сделать это "отдельной фичей"): тумблер вкл/выкл + тот же
чекбокс-пикер серверов, сгруппированный по подписке, что у профилей, плюс
блок "сейчас" с текущим выбранным шлюзом и размером пула. Реализовано
одинаково в LuCI (`view/xkeen-smartroute/doublevpn.js`) и в отдельной
панели (`gateway/static/doublevpn.js`) — оба говорят с одним и тем же rpcd
через `get_doublevpn_config`/`set_doublevpn_enabled`/`set_doublevpn_servers`
(см. [rpc-bridge.md](rpc-bridge.md)).

Изменение состава пула или тумблера сохраняется мгновенно, но реально
применяется (пересчёт шлюза + патч outbounds + возможный рестарт Xray) на
следующем `genroute.sh regen` — как через cron (до 3 минут), так и сразу же,
синхронно, самим вызовом `set-doublevpn-enabled`/`set-doublevpn-servers`
(оба вызывают `sr_regen 1` — `skip_fresh_ping`, то же самое сокращение, что
уже использует сохранение профиля, см.
[balancer.md](balancer.md#когда-происходит-пересчёт)).

## Сознательные ограничения

- **Действует глобально на все профили сразу**, не на выбранные. Пользователь
  описал фичу именно так ("перед всеми нашими конфигами") — опциональный
  per-профильный выбор "включить Double VPN только для этого профиля" не
  реализован, при необходимости это отдельное расширение поверх текущей
  схемы (например, поле `use_doublevpn` на профиле вместо глобального
  `enabled`).
- **`health.json`/страница "Подписки" начинают отражать достижимость через
  цепочку, а не напрямую**, пока фича включена — сервер, недостижимый
  напрямую, но доступный через шлюз, будет показан "жив". Это осознанно и
  соответствует цели фичи (именно эта достижимость и используется для
  реального трафика), но стоит иметь в виду при чтении статуса серверов на
  вкладке "Подписки" с включённым Double VPN.
- **Не чинит проблемы уровня REALITY-сертификата на самом destination**
  (см. живой тест выше) — только проблемы, вызванные блокировкой пути до
  сервера со стороны провайдера/сети. Оба типа "мёртвости" неотличимы друг
  от друга по `health.json` до включения Double VPN; после включения разница
  становится видна (первый тип оживает, второй — нет).
- **Если пул пуст или в нём нет ни одного достижимого сервера** — трафик
  остаётся прямым (без цепочки), а не блокируется; `doublevpn_current.json`
  показывает `gateway: null`. Значит "включено" не гарантирует, что цепочка
  реально активна прямо сейчас — это нужно проверять по `current`, не по
  одному только `enabled`.
