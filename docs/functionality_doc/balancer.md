# Балансировщик SmartRoute: Observatory, пинг и выбор сервера

Техническое описание того, как SmartRoute определяет "жив ли сервер" и выбирает,
через какой сервер пустить трафик профиля. Для более общего обзора фичи и истории
проблемы с `leastPing` Xray см. основной [README.md](../../README.md#как-выбирается-сервер-в-группе-и-почему-не-xray-leastping) —
этот документ — более глубокий разбор именно механики: что конкретно измеряется,
как устроен код, и почему он устроен именно так, с реальными числами из живого
тестирования.

## Два независимых сигнала: пинг и Observatory

### 1. Быстрый TCP-пинг (`sr_ping_tags`, `lib/subscription.sh`)

Голое TCP-подключение к `host:port` сервера, без какого-либо прокси-протокола
поверх. Быстро (сотни мс на сервер), но проверяет только "порт открыт и
принимает соединение" — ничего не говорит о том, работает ли реально VLESS/REALITY
поверх него. Сервер со сломанным REALITY-камуфляжем (например, provider перестал
отдавать нужный сертификат) отвечает на голый TCP-коннект мгновенно и выглядит
живым, хотя реальный прокси-трафик через него не пройдёт.

### 2. Observatory (`app/observatory` в самом Xray-core)

Настоящая проверка — Xray сам, изнутри, устанавливает полное VLESS/REALITY-соединение
через конкретный outbound и делает через него `GET` на тестовый URL. Это ровно то
же самое, что происходит при реальном подключении пользователя, просто с заранее
известным адресом.

Механика (вычитано из реального исходника `app/observatory/observer.go`
XTLS/Xray-core, не по памяти):

- Конфиг (`07_observatory.smartroute.json`, генерируется `sr_regen()`):
  `probeUrl: "https://www.gstatic.com/generate_204"`, `probeInterval: "1ms"`,
  `subjectSelector` — список тегов outbound'ов, которые нужно проверить (подробнее
  ниже — этот список у нас не статичный).
- На каждый тег из `subjectSelector`: полный хендшейт через именно этот outbound,
  затем `GET probeUrl`. Два жёстких таймаута по 5 секунд — на TLS-хендшейк и на
  весь HTTP-запрос целиком (`TLSHandshakeTimeout: 5s`, `http.Client.Timeout: 5s`).
- **`Alive = true` тогда и только тогда, когда `httpClient.Do(req)` не вернул
  ошибку транспорта.** HTTP-статус-код ответа **не проверяется вообще** — даже
  403/500 засчитывается как "жив". Мёртвым делает только уровень транспорта:
  connection refused, TLS handshake timeout, обнаруженный REALITY-редирект
  (`"REALITY: received real certificate (potential MITM or redirection)"`),
  обрыв соединения.
- **`Delay`** — wall-clock время от момента перед отправкой запроса до закрытия
  тела ответа. Это реальный полный RTT через прокси, включая хендшейт — не голый
  пинг. Если сервер мёртв, `Delay` жёстко ставится в `99999999` (маркер, не
  реальное число).
- Пробы идут **строго последовательно**, никогда параллельно
  (`enableConcurrency` у нас сознательно выключен — на слабом железе без свопа
  параллельные TLS/REALITY-хендшейты по нескольким outbound'ам разом роняли роутер
  в OOM, см. `AGENTS.md`). После каждой пробы (успешной или нет) — пауза
  `probeInterval` перед следующим тегом.
- `probeInterval: "1ms"` — это НЕ ограничение конкурентности (та по-прежнему
  строго 1 соединение в моменте), это просто пауза между пробами. Раньше стояло
  `"30s"`, что на подписке из ~130 серверов давало нижнюю границу обхода
  `130 × 30с ≈ 65 минут` — почти всё время съедала сама пауза, не запросы.
  Буквальный `"0s"` использовать нельзя: в `observer.go` есть проверка
  `if o.config.ProbeInterval != 0`, и если значение ровно ноль, Xray молча
  откатывается на свой дефолт в 10 секунд — обратный эффект. `"1ms"` — это
  практический ноль.

**Реальные цифры с живого роутера** (45 успешно опрошенных серверов, после
перехода на `probeInterval: "1ms"`): **min 373 мс, max 4833 мс (уже почти
таймаут), среднее ≈ 1048 мс**. Из первых ~80 опрошенных 36 оказались мёртвыми —
почти половина каждый раз съедает полный 5-секундный таймаут впустую, что и
определяет реальную скорость обхода куда больше, чем сама проба живого сервера.

Xray хранит эти данные **только в оперативной памяти процесса** (`o.status` в
`observer.go`) — при любом рестарте Xray (`xray run` перезапускается целиком)
эта таблица обнуляется полностью, независимо от причины рестарта.

## Как выбирается топ-1 сервер профиля (`sr_pick_top1`, `lib/genroute.sh`)

Два сигнала выше объединяются в 4-уровневый рейтинг (лучший — первый):

0. Свежий пинг прошёл **И** Observatory говорит "жив" — оба сигнала согласны.
   Сортировка по реальной задержке из Observatory (`delay_ms`), не по пингу.
1. Свежий пинг прошёл, но Observatory ещё не успел добраться до этого тега в
   текущем цикле — достижим, но не подтверждён ни в одну сторону.
2. Свежий пинг прошёл, но Observatory говорит "мёртв" — реальный негативный
   вердикт важнее отсутствия вердикта, поэтому этот уровень ниже предыдущего.
3. Свежий пинг вообще не прошёл — последний резерв.

Если данных нет вообще ни по одному сигналу — берётся первый сервер из пула
профиля. Свежий пинг здесь — не по всей подписке, а только по серверам,
перечисленным именно в этом профиле (`sr_ping_tags`, обычно десятки, не сотни
тегов) — недорого делать при каждом regen.

## Проблема: Xray сбрасывает Observatory на каждом рестарте

`sr_regen()` перезапускает Xray каждый раз, когда реально меняется файл
маршрутизации — а он меняется каждый раз, когда `sr_pick_top1` выбирает другой
топ-сервер для какого-то профиля. При свежем пинге кандидаты часто идут "ноздря
в ноздрю", так что выбор реально флипается между близкими соседями каждые
несколько минут — это подтверждено напрямую: за один цикли cron (3 минуты) тег,
выбранный для профиля Telegram, поменялся с одного сервера на другой.

А поскольку Observatory живёт только в памяти процесса, **любой** такой рестарт
обнуляет весь накопленный прогресс целиком — не только для той части подписки,
которая изменилась, а вообще для всех тегов. Xray при этом всегда идёт по
`subjectSelector` **строго по алфавиту тега** (`sort.Strings(outbounds)` в
`observer.go`) — никакого понятия "приоритет" или "продолжить с того места, где
остановился" в самом Xray нет вообще, это жёстко зашито в коде.

Итог при старом подходе (`subjectSelector: ["sr_"]`, то есть буквально все
серверы подписки): на реальном тесте прогресс застревал в районе 60-80 из 130
серверов и не сдвигался — каждый рестарт откатывал Xray к тем же самым
алфавитно-первым тегам, а до второй половины списка обход просто никогда не
успевал дойти.

## Наше решение: приоритетный список на основе "протухания"

Раз Xray нельзя попросить продолжить с прерванного места или расставить
приоритеты — вместо этого мы **на каждом regen пересчитываем `subjectSelector`
заново**, и он всегда маленький:

1. Собираем `profile_tags` — объединение серверов из ВСЕХ профилей (и `.servers`
   для balancer-режима, и `.fixed_server` для fixed) — весь пул кандидатов,
   не только сегодняшний победитель.
2. Для каждого тега смотрим `health.json` (персистентная копия данных
   Observatory, которую пишет `smartroute-gateway`, о ней ниже) — тег считается
   **протухшим** (`stale`), если записи нет вообще, или `checked_at` старше
   настраиваемого периода (`time_period_observatory`, по умолчанию 20 минут).
3. Если среди `profile_tags` есть хоть один протухший — `subjectSelector` = **только
   протухшие профильные теги**. Список маленький (обычно десятки), Xray успевает
   пройти его целиком в течение одного цикла cron.
4. Если все профильные теги свежие — `subjectSelector` = протухшие теги из
   **остальной части подписки** (серверы, не используемые ни в одном профиле).
5. Если протухших нет вообще нигде — `subjectSelector` пустой. `Observer.Start()`
   в этом случае просто не запускает фоновый цикл (`len(SubjectSelector) != 0`
   в условии) — Xray не гоняет пробы впустую, пока следующий regen не найдёт
   что-то протухшее.

Ключевая деталь: этот механизм **не нуждается в отдельном флаге "обход в
процессе / завершён"**. `checked_at` в `health.json` — уже единственный
источник истины о том, что сделано, а что нет, и он переживает рестарт Xray
(в отличие от внутренней памяти самого Xray). Тег выпадает из списка ровно в
момент, когда его свежо перепроверили, и не возвращается, пока не протухнет
снова — значит, повторно просканировать уже сделанную работу физически
невозможно, а если рестарт прервал текущий проход на середине — теряется
максимум одна проба, которая была "в полёте" в этот момент (плюс до 20 секунд
задержки опроса `smartroute-gateway`), а не весь накопленный прогресс.

## Реальный пример: как список сужается на живом роутере

Живой тест с реального роутера, сегодняшний (все теги реальные, из подписки
`gussitrade`):

**Regen №1** — среди тегов профилей нашлось 5 протухших:

```
[
  "sr_gussitrade_89_108_78_125_9443_a43f2687_",
  "sr_gussitrade_89_108_78_125_2083_a43f2687_",
  "sr_gussitrade_87_249_49_35_443_HXDAmbp5_",
  "sr_gussitrade_87_249_49_35_2083_a43f2687_",
  "sr_gussitrade_93_88_203_174_9443_c429fe25_youtube_4"
]
```
Лог: `regenerated routing (6 rule(s)), observatory watching 5 stale tag(s)`

**~40 секунд спустя, regen №2** — эти 5 успели свежо перепроверится (Xray
успевает пройти список из 5 тегов за секунды, не минуты), профильные теги
закончились, и селектор автоматически переключился на "остальную подписку":

```
[
  "sr_gussitrade_45_91_138_170_8765_c429fe25_2",
  "sr_gussitrade_89_108_78_125_8443_a43f2687_",
  "sr_gussitrade_77_91_66_136_443_525253ff_",
  ... (всего 40 тегов)
]
```
Лог: `regenerated routing (6 rule(s)), observatory watching 40 stale tag(s)`

Ни один из этих 40 тегов не совпадает с первыми 5 — подтверждает, что приоритет
и переключение тиров реально работают, а не просто совпадение.

## Когда происходит пересчёт

`sr_regen()` вызывается из нескольких мест:

- **Cron, раз в 3 минуты** (`*/3 * * * * genroute.sh regen`) — основной, регулярный
  пересчёт: свежий пул-скоуп пинг для balancer-профилей + пересчёт
  `subjectSelector` по протуханию.
- **Сохранение/удаление профиля через UI** (`genroute.sh save`/`delete`) —
  вызывается с флагом `skip_fresh_ping=1`: интерактивное сохранение не может
  ждать сетевой пробы всего пула (см. ниже), ранжирование идёт по уже
  накопленным `ping.json`/`health.json`.
- **Защищено mutex'ом** (`mkdir "$SR_STATE_DIR/.regen.lock"`) — если предыдущий
  вызов ещё не закончился, новый просто пропускается (не встаёт в очередь и не
  запускается параллельно), лок считается зависшим и перехватывается только
  через 300 секунд бездействия.

Рестарт Xray происходит только если реально изменился **хотя бы один** из двух
файлов — `05_routing.smartroute.json` (сменился топ-пик какого-то профиля) или
`07_observatory.smartroute.json` (сменился список протухших тегов). Если оба
байт-в-байт совпадают с тем, что уже на диске — рестарт пропускается целиком,
лог пишет `unchanged -- skipping restart`.

### Почему не пинг/Observatory всего пула при каждом подключении

Разбирали и сознательно отклонили: пинговать/перепроверять Observatory-ем весь
пул профиля (десятки серверов) при каждом срабатывании правила добавило бы
реальную задержку (секунды на подключение) на каждый новый сайт, который
открывает пользователь — и обычный TCP-пинг всё равно не поймал бы поломку
уровня REALITY-протокола (см. выше). Вместо этого профильные теги просто
получают приоритет в фоновом цикле выше — без блокировки самого подключения.

## Устойчивость данных между перезапусками

`smartroute-gateway` (`gateway/failover.go`) раз в 20 секунд читает состояние
Observatory через `ObservatoryService.GetOutboundStatus` (реальный gRPC-вызов к
Xray, снимок его внутренней таблицы) и сохраняет в `/etc/xkeen-smartroute/state/health.json`
— **не перезаписывая файл целиком**, а мёржа новые данные поверх старых
(`persistHealth()`): тег, который Xray ещё не успел перепробовать после своего
рестарта, не пропадает из файла, а просто "стареет" по `checked_at`.

Была найдена и исправлена реальная проблема с этим механизмом: `persistHealth()`
писала файл напрямую (`os.WriteFile` в конечный путь), не атомарно. Запись идёт
каждые 20 секунд весь день — если питание пропадает ровно в момент записи, файл
может остаться обрезанным/битым, а на следующем старте `json.Unmarshal` от
битого файла тихо проглатывает ошибку (`_ = json.Unmarshal(...)`) и код
трактует это как "старых данных нет", переписывая файл уже почти пустым.
Исправлено: запись теперь идёт во временный файл в той же директории, затем
атомарный `os.Rename` поверх целевого — на диске всегда либо полностью старая,
либо полностью новая версия файла, никогда не половина.

## Настройка `time_period_observatory`

Задаётся на вкладке **Подписки** (`sr.rpc.getObservatoryPeriod`/`setObservatoryPeriod`,
CLI: `genroute.sh get-observatory-period` / `set-observatory-period <минуты>`,
хранится в `/etc/xkeen-smartroute/state/observatory_period_min`). По умолчанию
**20 минут** — компромисс между свежестью данных и тем, что полный проход по
паре сотен серверов (при `probeInterval: "1ms"`, ~1 сек среднее на пробу)
комфортно укладывается в один период, даже если рестарты его прерывают.

## Сознательные ограничения

- **Никакого `routing.balancers`/`balancerTag`.** Подтверждённый баг в
  используемой версии Xray-core: наличие *любого* правила с `balancerTag` в
  `routing.rules` полностью останавливает совпадение **всех** правил маршрутизации
  целиком — не только самого balancer-правила. Воспроизведено на живом железе
  методом исключения, заведён баг-репорт апстрим:
  [XTLS/Xray-core#6642](https://github.com/XTLS/Xray-core/issues/6642). Поэтому
  `sr_pick_top1` эмитит обычное `outboundTag`-правило (тот же механизм, что
  `mode: "fixed"` уже использовал и он подтверждённо работает), а не полагается
  на встроенный `leastPing`.
- **Порядок обхода внутри одного тира — алфавитный, не по важности.** Xray сам
  не даёт возможности задать порядок иначе; в рамках профильного тира это не
  критично (список маленький, весь укладывается в один цикл).
- **Полный список подписки без profile-привязки** проверяется лениво, только
  когда все профильные теги свежие — сервер, не используемый ни в одном профиле,
  может подолгу оставаться "не проверен", если профилям постоянно есть что
  обновить. Это осознанный компромисс: `sr_pick_top1` в любом случае никогда не
  смотрит на такие серверы.
- **Жёсткий 5-секундный таймаут даёт небольшой, но реальный процент ложных
  смертей** — подтверждено вживую: выборка из 8 разных "мёртвых" серверов,
  каждый напрямую проверен через изолированный тестовый Xray-процесс с
  таймаутом 15с вместо 5 — 1 из 8 оказался живым (ответил `204` за 8.3с, просто
  чуть медленнее потолка), 7 из 8 не ответили даже за 15с (реально мертвы).
  Экстраполируя на всю подписку — единицы серверов ложно висят мёртвыми в любой
  момент времени, не десятки.

  **Рассмотрена и отклонена альтернатива**: у Xray-core есть `burstObservatory`
  — тот же `GetOutboundStatus` gRPC (ноль правок в `gateway/xray.go`), но с
  настраиваемым `pingConfig.timeout`. Подтверждено вживую (изолированный тестовый
  процесс, тот же самый ложно-мёртвый сервер) — с 15-секундным таймаутом
  корректно определяется как живой. Но чтение реального исходника
  (`app/observatory/burst/healthping.go`) показало: `doCheck()` пингует **все**
  теги из `subjectSelector` через `time.AfterFunc` с нулевой задержкой на каждом
  первом проходе после рестарта — то есть параллельно, не последовательно. Это
  ровно тот паттерн, который уже реально ронял этот роутер по памяти (поэтому
  `enableConcurrency` у обычного observatory сознательно выключен, см. выше) —
  список `subjectSelector` у нас регулярно доходит до нескольких десятков тегов
  (см. "Реальный пример" ниже), так что переход на `burstObservatory` целиком
  реинтродуцировал бы тот самый OOM-риск. Отдельно найден и не связанный со
  своей стороны баг самого Xray — `Delay` у `burstObservatory` иногда
  отрицательный (`-1644`, `-707`; видимо, дефект расчёта среднего в
  `getStatistics()` при малом числе сэмплов), пришлось бы клампить перед
  использованием в `sr_pick_top1`.

  Осознанно оставлено как есть — риск OOM важнее, чем единицы ложных "мёртв" на
  фоне 92 из 152 реально помечаемых мёртвыми серверов. Если понадобится
  переоценить — тестовая методика (изолированный `xray run -confdir` со своим
  портом API, отдельный gRPC-клиент на Go для прямого запроса
  `ObservatoryService.GetOutboundStatus`) полностью воспроизводима, ничего
  боевого не трогает.
