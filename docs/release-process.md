# Схема веток и релизов

Как устроена разработка, версионирование и публикация в этом репозитории — чтобы
история и `Releases` были предсказуемыми, а не вперемешку из бинарников, списков
доменов и случайных коммитов.

## Ветки

- **`master`** — единственная стабильная ветка. Только сюда попадает
  протестированный, рабочий результат. **Все публикуемые артефакты (бинарники
  `smartroute-gateway`, GitHub Releases, всё, что тянет `install.sh`) собираются
  только из `master`.** Никаких прямых пушей в обход `develop`, кроме реальных
  горячих фиксов (см. ниже).
- **`develop`** — рабочая интеграционная ветка. Сюда мёржатся фича-ветки по мере
  готовности. `develop` может быть менее вылизанной, чем `master`, но не должна
  быть постоянно сломанной — это следующий кандидат на релиз, не свалка.
- **Фича-ветки** — без строгого нейминга, живут до мержа в `develop`, потом
  удаляются. Один PR/мерж — одна законченная тема (баг-фикс, фича, рефактор).
- **Периодически**: когда состояние `develop` стабильно и прогнаны тесты
  (в первую очередь — реальная проверка на живом роутере, не только код-ревью,
  см. `AGENTS.md`) — `develop` мёржится в `master`, и на этом коммите ставится
  тег релиза.

## Версии (теги)

Формат `vMAJOR.MINOR.PATCH` (синтаксис SemVer, но со своей смысловой нагрузкой —
не о breaking changes, а о значимости релиза):

- **MAJOR** — большой релиз, которым можно гордиться: новая крупная фича,
  архитектурный сдвиг (пример из истории проекта — замена сломанного
  `balancerTag` собственным алгоритмом выбора сервера).
- **MINOR** — обычный, нормальный релиз: доработка, заметное улучшение, но не
  событие уровня MAJOR.
- **PATCH** — быстрый, "стыдный" фикс мелкого бага.

Примеры: `v2.7.0` — крупный релиз; `v2.7.1` — мелкий фикс поверх него; `v2.8.0` —
следующая обычная доработка; `v3.0.0` — следующий крупный релиз.

### Зачем тегов достаточно — почему релизных веток нет

Тег сам по себе уже даёт возможность собрать себе конкретную версию —
`git checkout v1.2.4`, `git clone --branch v1.2.4 <repo>`, скачивание zip с
конкретного тега на GitHub — всё это работает с тегом точно так же, как с
веткой, и тег никуда не денется (пока его не удалят вручную). Заводить
отдельную ветку на каждый релиз (`release/vX.Y.Z` и т.п.) ради одной только
этой цели избыточно — особенно учитывая, что PATCH-релизы в этом проекте
выходят часто (несколько за один день — не редкость), так что ветки на
каждый тег быстро превратились бы в мусор, которым никто не пользуется.

Настоящий смысл у release-веток появляется только для **бэкпорта фиксов в
старые версии** параллельно с разработкой новых (LTS-ветки у Node.js,
`release-1.28` у Kubernetes и т.п.) — но это отдельная, тяжёлая практика
поддержки нескольких версий одновременно, которая прямо противоречит
текущей философии проекта («`master` — единственная стабильная ветка», см.
выше). Если это когда-нибудь понадобится — заводить release-ветки нужно
осознанно под эту конкретную задачу, а не просто "на будущее".

### Хотфиксы

Срочный фикс поверх уже выпущенного `master` (не через обычный цикл
`develop → master`) помечается **build-metadata суффиксом `+hotfix`**, не
pre-release суффиксом через дефис:

```
v16.8.35+hotfix    # правильно
v16.8.35-hotfix    # НЕ так
```

Причина: GitHub при автоопределении "Latest release" **игнорирует теги с
дефисом** — это pre-release синтаксис SemVer, он специально считается ниже по
приоритету, чем обычный тег с теми же цифрами, поэтому такой тег никогда
автоматически не станет "latest" (сломает `gateway-latest`/автообновление).
`+` (build metadata) на сортировку версий не влияет — `v16.8.35+hotfix`
воспринимается как ровно `v16.8.35` по приоритету, просто с пометкой в
названии.

Сам хотфикс либо коммитится прямо в `master` (для действительно тривиального
исправления), либо — для чего-то чуть более сложного — в короткоживущей ветке
`hotfix/<название>` от `master`, которая после мержится **и в `master`, и
обратно в `develop`** (чтобы тот же баг не вернулся с следующим обычным
релизом, который придёт из `develop`).

## CI и публикация

Сборка и публикация артефактов (`build-gateway.yml` и т.п.) триггерится **по
пушу тега `v*` на `master`**, а не по каждому пушу в саму ветку `master`.
Причина: момент "смёржили в master" и момент "готовы выпустить релиз" — не
всегда один и тот же момент (после мержа может понадобиться финальная проверка
на живом роутере перед тем, как отдавать бинарник пользователям) — тег как
явное, осознанное действие "публикуем" развязывает эти два события.

## Разделение каналов релизов

`Releases` раньше мешал в одну кучу версии приложения, бинарники и
автообновляемые списки доменов — то, что реально должно быть разными каналами:

- **Версии приложения** (`vX.Y.Z`) — то, что описано выше: сборки
  `smartroute-gateway`, changelog, привязка к конкретному коммиту `master`.
- **Списки доменов** (`Character.AI`/`Grok`/`npm` и т.п., автообновляемые через
  `update-domain-lists.yml`) — это не версия приложения, а постоянно
  обновляемые данные. Публикуются под отдельным, не связанным с семвером
  вечным тегом (по аналогии с уже существующим `gateway-latest` для бинарника
  gateway) — обновляются на месте, не плодят новую запись в истории версий
  приложения на каждое изменение списка.

## CHANGELOG.md

Ведётся в стиле [Keep a Changelog](https://keepachangelog.com/) — секция на
каждый тег, кратко что добавлено/исправлено/изменено. Обновляется в том же
коммите/PR, что и сам релиз, до простановки тега.

## Итоговый цикл одной фичи

1. Ветка от `develop` (любое название).
2. Работа, коммиты, реальная проверка на живом роутере (не только "код
   выглядит правильно" — см. методологию в `AGENTS.md`).
3. Мерж в `develop`.
4. Когда `develop` накопил стабильный, готовый к выпуску результат — мерж в
   `master`.
5. Запись в `CHANGELOG.md`, тег `vX.Y.Z` (или `vX.Y.Z+hotfix` для срочных
   фиксов мимо обычного цикла) на коммите в `master`.
6. Тег триггерит сборку и публикацию — CI собирает бинарники именно с этого
   коммита `master`, ничего до тега пользователям не попадает.
