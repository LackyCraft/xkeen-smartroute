# Интерфейс SmartRoute: вкладки и их нефункциональные особенности

Обзор всех пяти вкладок LuCI-модуля — что на них есть, и, что важнее,
**нефункциональные нюансы**: что означают конкретные индикаторы, почему
некоторые вещи выглядят непривычно, но так и задумано. Про саму логику
выбора сервера — [docs/balancer.md](balancer.md), про обновление подписки

## Подписки / Subscriptions

- Форма добавления: ссылка-подписка, название, пресет клиента (17 штук —
  Happ, v2rayNG, Clash и т.д.) с возможностью вручную переопределить
  заголовки устройства.
- Список серверов по каждой подписке, сворачиваемый: имя, `host:port`,
  протокол, пинг (TCP), статус Observatory (цветная точка + время
  последней проверки).
- Настройка автообновления подписки (галочка + короткое предупреждение) и
  интервала в часах, кнопка «Обновить сейчас».
- Настройка периода Observatory (`time_period_observatory`) — насколько
  старым должен быть результат, чтобы сервер снова попал в очередь на
  проверку.

### Про колонку "жив/мёртв" — почему сразу много серверов показывают "только что"

Это не глюк отображения — так и задумано, но стоит понимать механизм,
чтобы не удивляться. `checked_at` — это **не** "когда именно Xray
перепроверил этот конкретный сервер", а "когда наш гейтвей в последний раз
опросил внутреннюю таблицу Xray и увидел там эту запись" (гейтвей опрашивает
раз в 20 секунд и штампует **всё**, что видит в таблице, одним и тем же
моментом — подтверждено на практике: десятки записей с идентичным
timestamp'ом до наносекунды). Xray сам обновляет записи в этой таблице
гораздо реже и не все разом (см. приоритетную очередь в
[docs/balancer.md](balancer.md#наше-решение-приоритетный-список-на-основе-протухания)).
Так что "мёртв" — это честно, а вот "только что" у "живых" иногда означает
"гейтвей только что заглянул в таблицу", не всегда "прямо сейчас
перепроверено". Сам факт alive/dead при этом достоверен.

## Профили / Profiles

- Форма создания профиля: имя, источник доменов (любой / geosite-категория
  / свой список), устройства (Policy-Based Routing, чекбоксы + ручной
  ввод IP/CIDR), IP-диапазоны (для приложений вроде Telegram, которые не
  маршрутизируются по домену — см.
  [README](../README.md#что-добавляет-smartroute)), режим (конкретный
  сервер / группа с авто-выбором), выбор серверов (сгруппировано по
  подписке, сворачиваемо).
- Таблица существующих профилей: имя, домены, **целевой сервер**,
  действия.

### Зелёная точка "online now" — что это на самом деле

Это то, что физически показывает "через какой сервер я прямо сейчас реально
сижу на сайте" — и это **не** Observatory. Точка основана на **реальных
байтовых счётчиках трафика** конкретного outbound'а (гейтвей опрашивает их
каждые 3 секунды через `StatsService` самого Xray) — загорается зелёным,
только если через именно этот сервер прямо сейчас идут байты.

- В **свёрнутом** виде (по умолчанию) в строке профиля показан только
  **один** сервер — тот, что балансировщик выбрал прямо сейчас — с его
  собственной точкой. Это и есть ответ на "через какой сервер я сейчас
  смотрю YouTube".
- В **развёрнутом** виде (весь пул кандидатов) у каждого кандидата тоже
  своя точка — и здесь есть нюанс: Observatory сама периодически шлёт
  мини-запрос через **каждый** кандидат в пуле (проверка живости), и это
  тоже настоящий трафик через тот outbound — точка кандидата, который
  сейчас реально не используется для маршрутизации, может на мгновение
  мигнуть зелёным именно поэтому. Это не признак того, что через него
  тоже идёт ваш трафик — только то, что Observatory его в этот момент
  проверяет.
- Красное предупреждение под строкой профиля (если есть) — сервер(а),
  пропавшие из пула при последнем обновлении подписки (подробности в
  [docs/subscription-update.md](subscription-update.md)); пропадает само
  при следующем сохранении профиля через UI.

## Статус / Status

- Карточки трёх сервисов (Xray / панель SmartRoute-gateway / xkeen-UI):
  живой статус + старт/стоп/рестарт по отдельности.
- Ссылки на xkeen-UI (порт 1000) и панель SmartRoute (порт 1001).
- Обзор: сколько серверов/профилей всего, таблица по подпискам.
- Метрики здоровья: живых/мёртвых/непроверенных серверов, когда последний
  раз обновлялась подписка, когда последний раз пересчитывался пинг, когда
  последний раз реально проверялся Observatory, сколько серверов сейчас в
  очереди на проверку Observatory.
  - «Последняя проверка Observatory» — та же особенность, что и в разделе
    Подписок выше: это самый свежий `checked_at` среди всех серверов, и
    из-за механизма штамповки он почти всегда будет "только что", даже
    если Observatory физически ничего нового не проверила в этот момент.
  - «В очереди на проверку» — число может сильно скакать (то пара штук, то
    несколько десятков) — это нормально, отражает работу приоритетного
    планировщика: как только что-то протухает, оно попадает в очередь и
    быстро вычищается.
- Живой график трафика (реальные байтовые счётчики, тот же источник, что и
  точка "online now" в Профилях).

## Kill-Switch

- Одна галочка на каждый профиль (домен-ориентированные — geosite и свои
  списки).
- «Жёсткий» kill-switch: если процесс Xray падает (или пропадают правила
  перехвата трафика), домены профиля блокируются файрволом **полностью**,
  вместо риска утечки напрямую в обход VPN. Правило работает постоянно
  через `nftables`, не опрашивается раз в минуту — зазора по времени, в
  котором утечка теоретически возможна, нет.
- Для geosite-категорий покрытие **неполное** — переносятся только
  буквальные записи `domain:`/`full:` из исходного списка geosite;
  `keyword:`/`regexp:`-паттерны (это не конкретные домены, а правила
  сопоставления) в файрвол не переносятся. Отмечено прямо в интерфейсе
  рядом с такими профилями.

## Защита от утечек / Leak protection

- **Перехват LAN-трафика** (вкл/выкл + список портов) — базовый механизм,
  без которого ни один профиль или kill-switch вообще не видит трафик
  устройств (свой `nftables`-редирект, обходит проблему `xkeen -ap` на
  чистом OpenWrt — подробнее в README, раздел «Кроссплатформенность»).
  Выключать стоит только для диагностики.
- **Защита DNS** — принудительно заворачивает все DNS-запросы (порт 53) с
  LAN на сам роутер, даже если устройство прописано на сторонний DNS.
  Без этого запросы могут уходить напрямую мимо VPN, а kill-switch не
  увидит домены для блокировки.
- **Блокировка IPv6** — перехват работает только для IPv4; сайт,
  доступный по IPv6, иначе мог бы открыться напрямую через провайдера в
  обход всех правил. Опция полностью блокирует LAN→WAN IPv6.
- **Блокировка QUIC/HTTP3** — перехват ловит только TCP; сайты с
  поддержкой HTTP/3 браузер может открыть по QUIC (тот же порт 443, но по
  UDP) в обход перехвата целиком — подтверждено на практике. Опция
  блокирует исходящий UDP на перехватываемых портах; браузеры при этом
  просто откатываются на обычный TCP/TLS, без потери функциональности.
