# XKeen SmartRoute DanyByLC

**Русский** | [English](README.EN.md)

Разворачивание одной командой точечной маршрутизации по доменам через VLESS/Trojan-подписку на роутерах с OpenWrt: `xkeen` (менеджер Xray-core) + `xkeen-UI` + наш модуль **SmartRoute** (LuCI), который добавляет то, чего нет ни в одном из них "из коробки" — привязку списков доменов к конкретным серверам подписки и автоматический выбор самого быстрого сервера в группе.

> Проект вдохновлён [itdoginfo/domain-routing-openwrt](https://github.com/itdoginfo/domain-routing-openwrt), но собран под другой стек — `xkeen`/Xray-core вместо AmneziaWG/WireGuard, и вокруг VLESS-подписок, а не отдельных ключей.

## Зачем это нужно

У вас есть одна VLESS/Trojan-подписка (как для V2rayNG/V2Box) с кучей серверов в разных странах. Стандартный клиент даёт выбрать *один* сервер для всего трафика. SmartRoute позволяет настроить это точечно прямо из веб-интерфейса роутера:

- «Весь YouTube → сервер в Германии»
- «Discord → берём самый быстрый из трёх выбранных серверов, и Xray сам постоянно перепроверяет, какой из них быстрее»
- «Character.AI/Grok (их нет в стандартной базе доменов Xray) → отдельный сервер»
- «Если процесс Xray упал — не пускать эти домены в интернет напрямую в обход VPN»

Всё остальное (не попавшее ни в один профиль) идёт как обычно — напрямую или через основной выход, который вы настроите сами в `xkeen`/`xkeen-UI`.

## Как это работает

```
[Ваша VLESS/Trojan подписка]
        │
        ▼
 SmartRoute: subscription.sh  ──► список серверов (servers.json)
        │
        ▼
 LuCI-модуль SmartRoute (веб-интерфейс)
   • выбираете список доменов (geosite-категория Xray ИЛИ наш файл)
   • выбираете: 1 конкретный сервер, ИЛИ группу серверов
        │
        ▼
 SmartRoute: genroute.sh ──► routing.json + balancer.json (для Xray)
        │
        ▼
      xkeen (управляет Xray-core) ──► реально шлёт трафик
        │
        ▼
    xkeen-UI (порт 1000) — отдельная панель для сервисных задач:
    редактор конфигов, логи, обновление ядра/geosite/geoip
```

Автоматический выбор самого быстрого сервера в группе — это встроенный механизм Xray-core, **balancer со стратегией `leastPing`** поверх `observatory` (Xray сам пингует все сервера группы и держит живым/выключенным маршрут). SmartRoute просто генерирует для него конфиг по вашему выбору в UI — никакого велосипеда поверх Xray нет, это официальная возможность ядра.

## Что умеет xkeen

[`xkeen`](https://github.com/Skrill0/XKeen) — консольный менеджер Xray-core (и опционально ядра Mihomo/Clash), который ставится через **Entware** (opkg-совместимый пакетный менеджер для встраиваемых систем, в том числе OpenWrt).

- Протоколы: **VLESS** (включая Reality, TLS, транспорты tcp/ws/grpc/xhttp), **VMess**, **Trojan**, **Shadowsocks**.
- Два ядра на выбор: **Xray-core** и **Mihomo (Clash)** — переключение одной командой.
- Конфиг Xray собирается из отдельных JSON-фрагментов в `/opt/etc/xray/configs/` (наши `04_outbounds.smartroute.json`, `05_routing.smartroute.json`, `09_balancer.smartroute.json` — ровно в этом месте).
- Управление сервисом: `xkeen -start` / `-stop` / `-restart` / `-status` / `-auto`.
- Обновления: `-uk` (ядро), `-ux` (Xray), `-um` (Mihomo), `-ug` (geosite/geoip базы доменов и IP-подсетей).
- Включение/исключение по портам: `-ap`/`-dp`/`-ape`/`-dpe`.
- Резервное копирование и восстановление конфигурации: `-kb` / `-kbr`.
- Диагностика: `-diag`, `-tpx`.
- Работает как локальный HTTP/SOCKS-прокси и/или через firewall-редирект (в зависимости от вашей схемы) — маршрутизация по домену/IP реализуется через `routing.rules` Xray-core, что и использует SmartRoute.

> У `xkeen` нет встроенной команды импорта подписки — это (как и остальной функционал SmartRoute) добавляет наш модуль.

## Что умеет xkeen-UI

[`xkeen-UI`](https://github.com/zxc-rv/XKeen-UI) — отдельная веб-панель для `xkeen`, статический Go-бинарник, работает на **порту 1000**, ничего общего с LuCI не имеет (это самостоятельный сервис).

- Старт/стоп/статус сервиса Xray/Mihomo.
- Редактор конфигурационных файлов с проверкой синтаксиса.
- Просмотрщик логов (автообновление, фильтрация, часовой пояс).
- Переключение и обновление ядра (Xray ⇄ Mihomo).
- **Outbound Generator** — отдельная страница: вставляете ссылку из панели вроде 3X-UI → скачиваете готовый `outbounds.json`.
- Под ядром Mihomo — Clash API: пинг узлов по группам, закрепление/открепление ноды прямо в интерфейсе.

SmartRoute (наш LuCI-модуль + отдельная панель, см. [ниже](#панель-smartroute-и-почему-не-mihomo)) и xkeen-UI — независимые интерфейсы на одном стеке: xkeen-UI хороша для сервисных задач (логи, ручное редактирование конфига, апдейты ядра, бэкапы), SmartRoute — для повседневного «домен/устройство → сервер(а)» и живого мониторинга.

`install.sh` дополнительно один раз спросит пароль для входа в xkeen-UI (по умолчанию она открыта всем в сети без авторизации) и включит его — рекомендуем использовать тот же пароль, что и для входа на сам роутер.

## Что добавляет SmartRoute

Модуль `luci-app-xkeen-smartroute` (LuCI) + `smartroute-gateway` (отдельная панель, см. [ниже](#панель-smartroute-и-почему-не-mihomo)) — вот что добавляется поверх голого `xkeen`/`xkeen-UI`:

- **Импорт подписки** (VLESS/Trojan, формат V2rayNG/V2Box: base64-блок ссылок) — получаем список серверов из вашей подписки. Некоторые панели подписок отдают браузеру просто HTML-страницу с инструкцией, а настоящий список — только известным VPN-клиентам (по `User-Agent` и заголовкам устройства). На вкладке «Подписки» есть 17 готовых профилей клиента (Happ, v2rayNG, Clash/Clash Meta/Mihomo, sing-box, NekoBox, Shadowrocket, Stash, Surge, Loon, FlClash, V2Box, incy и др.) и ручные поля Device-OS/Device-Locale/Device-Model/X-Ver-Os/X-Hwid (с кнопкой генерации случайного HWID) — под «Настроить заголовки устройства…».
- **Автообновление подписки**: раз в настраиваемый интервал (по умолчанию 12 часов, задаётся прямо в интерфейсе) все сохранённые подписки перезапрашиваются заново, без участия пользователя. Обновление многосерверное: несколько подписок сразу не затирают серверы друг друга, а невалидный/пустой ответ от провайдера (временный сбой) не обнуляет уже сохранённые сервера — просто пропускается до следующей попытки.
- **Пинг серверов**: TCP-задержка до каждого сервера подписки прямо в интерфейсе (без раскрытия IP-адресов), параллельно по всем серверам разом.
- **Профили маршрутизации**: список доменов (geosite-категория Xray *или* свой список), **и/или** конкретные устройства сети (Policy-Based Routing — см. ниже) → конкретный сервер (`fixed`) *или* группа серверов с авто-выбором самого быстрого (`balancer` / `leastPing`).
- **Policy-Based Routing по устройствам**: профиль можно ограничить не только доменами, но и конкретными устройствами сети (по IP/CIDR) — «только телевизор идёт через VPN», независимо от того, какие сайты он открывает, или «только телевизор, только для YouTube» — оба ограничения сразу. Вкладка «Профили» показывает устройства, обнаруженные через DHCP-аренды и ARP-таблицу роутера (с именем и MAC-адресом, если известны), плюс поле для ручного ввода IP/CIDR — на случай устройства со статическим адресом или целой подсети.
- **Свои списки доменов на лету**: вписали домены через запятую в UI — тут же появился список, который можно привязать к серверу.
- **Готовые списки для того, чего нет в стандартной базе Xray (geosite)** — см. [ниже](#списки-доменов-которых-нет-в-geosite): сейчас это Character.AI, Grok/x.ai, npm registry — с автообновлением через GitHub Actions.
- **Защита от утечек DNS и IPv6**: отдельная вкладка «Защита от утечек» — принудительно заворачивает LAN-DNS на сам роутер, даже если устройство прописано на сторонний DNS (защита от обхода профилей/kill-switch мимо VPN), и опционально блокирует LAN→WAN IPv6 целиком, поскольку наш перехват трафика — только IPv4, а сайт, доступный по IPv6, иначе мог бы открыться напрямую через провайдера в обход всех правил.
- **Kill-switch без единого зазора по времени**: как только он включён для профиля — блокировка через firewall+ipset стоит постоянно, а не проверяется раз в минуту. DNAT-редирект трафика физически идёт через `INPUT`-цепочку firewall, а не `FORWARD`, поэтому правило-блокировка не мешает нормальной работе и включено всегда, без риска поймать «окно» между падением Xray и срабатыванием проверки (в котором раньше мог утечь настоящий IP). Работает и для собственных списков доменов, и для geosite-категорий. Подробнее — раздел [Интерфейс](#интерфейс) → Kill-Switch.
- **Настоящий failover внутри группы серверов**: у самого Xray-core связка `leastPing`+`observatory` умеет обнаруживать нерабочий сервер (пробный запрос реально идёт через сам сервер, включая REALITY-рукопожатие), но в текущих версиях ядра это не всегда останавливает выбор именно этого сервера для новых соединений — известный, пока не исправленный баг апстрима ([XTLS/Xray-core#5295](https://github.com/XTLS/Xray-core/issues/5295)). `smartroute-gateway` (см. ниже) закрывает этот пробел сам: читает те же данные наблюдателя и, если текущий выбор балансировщика подтверждённо мёртв, принудительно переключает его на самый быстрый живой сервер группы — тем же самым API-вызовом, что использует `xray api bo`.
- **Устойчивый перезапуск Xray**: перед каждым перезапуском конфиг валидируется (`xray run -test`) — если что-то не так (битый узел из подписки, рассинхронизация тегов после смены списка серверов), Xray не трогается и продолжает работать на старом рабочем конфиге вместо падения. На чистом OpenWrt (в отличие от родной для `xkeen` KeeneticOS) сам перезапуск идёт в обход `xkeen -restart`, который на такой платформе зависает намертво. Раз в сутки (по умолчанию — ночью) Xray дополнительно перезапускается по расписанию: на слабом железе без swap его память со временем растёт, и плановый перезапуск дешевле, чем ждать, пока это сделает за нас OOM-killer ядра.
- **Статус-панель**: жив ли Xray, сколько серверов и профилей настроено.
- **Панель SmartRoute** (`smartroute-gateway`, отдельный сервис на порту `1001`) — живой дашборд в духе Mihomo: список серверов с пингом, переключение сервера в профиле в реальном времени, график трафика, логи Xray — без переключения ядра на Mihomo. Подробности и почему так — [ниже](#панель-smartroute-и-почему-не-mihomo).
- Полностью на **русском и английском** (переключатель языка в самом интерфейсе — LuCI без сборочного SDK не даёт нормально подключить `.po`-переводы, поэтому язык встроен прямо в модуль; панель SmartRoute — так же).

## Кроссплатформенность: как SmartRoute чинит xkeen на OpenWrt

`xkeen` изначально написан под **KeeneticOS** — родную платформу Keenetic-роутеров. Entware (среда, где живут `xkeen`/Xray-core/весь наш стек) официально поддерживает и OpenWrt тоже, так что сам стек рабочий — но одна из встроенных возможностей `xkeen`, включение перехвата LAN-трафика по портам (`xkeen -ap`), на «чистом» OpenWrt 21.02+ не делает ничего, и вот почему.

На таком OpenWrt в ядре по умолчанию работает **nftables** (через фронтенд `fw4`), а не классический iptables. Но Entware ставит собственный, полностью независимый **legacy iptables** (`/opt/sbin/iptables` → `xtables-multi`) — и `xkeen -ap` пишет правила именно в него. Ядро при этом слушает только настоящий nftables-стек (`/usr/sbin/iptables`, на самом деле совместимый враппер `xtables-nft-multi`, либо сам `nft`). В результате `xkeen -ap 443,80` рапортует об успехе — а трафик реальных LAN-устройств продолжает идти мимо Xray, будто команда вообще не выполнялась. Мы подтвердили это напрямую на железе: `conntrack` показывал нулевую разметку (`mark=0`) и ноль соединений на редирект-порт Xray, даже когда `xkeen` считал порты уже включёнными. На родной KeeneticOS этого расхождения нет — там `xkeen` и работает с тем стеком, под который написан.

Поэтому SmartRoute добавляет собственный, независимый от `xkeen -ap` перехват трафика (`lib/redirect.sh`) — через официально поддерживаемую точку расширения `fw4`, каталог `/etc/nftables.d/`. Наш модуль кладёт туда свою nft-цепочку (перехват TCP 80/443 на редирект-инбаунд Xray, плюс опциональные правила для защиты от утечек DNS/IPv6), она переживает `fw4 reload`, `/etc/init.d/firewall restart` и перезагрузку роутера — и именно она делает возможной саму идею «маршрутизация по домену/устройству» на этой платформе. Без неё профили, kill-switch и Policy-Based Routing существовали бы только как корректный JSON-конфиг, до которого реальные пакеты с LAN не долетают.

## Панель SmartRoute и почему не Mihomo

У `xkeen` из коробки есть возможность переключить движок с Xray-core на **Mihomo** (форк Clash), у которого действительно красивая экосистема готовых веб-панелей (yacd, metacubexd и т.д.) — именно к такому уровню интерфейса мы и стремились. Но переключать сам движок мы не стали, по паре причин:

- **Конфиги Xray уже написаны и работают.** Весь модуль (профили, балансировщики, kill-switch) генерирует JSON именно под Xray-core (`routing.rules`, `routing.balancers` с `leastPing`). Переезд на Mihomo означал бы переписывать генератор конфигов под YAML-формат Clash с нуля — ради интерфейса, который можно получить и так.
- **Xray-core у нас уже отлажен под конкретное железо** (см. историю багов в [AGENTS.md](AGENTS.md) — от hardfloat/softfloat несовместимости до версии-скошенных конфигов). Смена движка означала бы проходить часть этого пути заново.
- Часть возможностей Mihomo (TUN-режим, DNS-сервер, полноценный Clash API из коробки) для нашего сценария избыточна — задача была именно точечная маршрутизация по доменам через существующую подписку, не полноценная замена всего сетевого стека.

Поэтому мы сделали своё: **`smartroute-gateway`** — маленький Go-сервис, который говорит с настоящим Xray-core через его собственный gRPC API (статистика трафика) и с состоянием SmartRoute (список серверов, профили) напрямую — и поверх этого отдаёт живую панель на порту **`1001`**, без переключения ядра.

Первая версия панели была построена на **metacubexd** (готовый open-source Clash-дашборд, тот же протокол) — но на практике выяснилось, что она рассчитана на полный набор возможностей Mihomo (учёт живых соединений, DNS-инструменты, редактор правил, десяток протоколов, которых у нас просто нет) и требует отдельного экрана подключения, из-за чего часть вкладок оставалась пустой при полностью рабочем бэкенде. Решили не подгонять чужой интерфейс под наши возможности, а написать свой — лёгкий, без сборки, ровно под то, что умеет SmartRoute:

- список серверов подписки с живым пингом;
- переключение сервера в профиле (или авто-выбор) прямо из панели — пишет в те же профили SmartRoute, что и LuCI, второго хранилища состояния нет;
- график трафика в реальном времени;
- лог Xray.

`smartroute-gateway` ставится и обновляется автоматически через `install.sh` (собирается в GitHub Actions под 5 архитектур: mipsle/mips-softfloat, arm7, arm64, amd64) и работает постоянным сервисом — не нужно ничего запускать вручную.

## Системные требования

**Роутер:**
- OpenWrt 21.02+ (проверено на актуальных 23.05/24.10); также должно работать на KeeneticOS с Entware (штатная среда для `xkeen`), если у вас Keenetic — сначала убедитесь, что на нём в принципе доступен shell/SSH.
- Архитектура: mips/mipsel, aarch64, armv7 или x86_64 (всё, для чего есть сборка Entware — практически все домашние роутеры последних 7-8 лет).
- Свободное место: `install.sh` стартует от **~25 МБ** свободных на overlay, но это впритык. Измерено на реальном тестовом роутере (92 МБ overlay): Xray-бинарник — 32 МБ, geosite/geoip базы — 19 МБ, xkeen-UI — 7 МБ, весь модуль SmartRoute (lib-скрипты, панель `smartroute-gateway`, списки доменов) — 33 МБ — итого **~90 МБ** только на сам стек, без учёта роста подписки/логов. Если во flash роутера столько нет, обязательно подключите **USB-флешку** и разверните Entware на ней (это стандартная практика, install-скрипт Entware сам предложит выбрать раздел).
- Оперативная память: от 128 МБ, комфортно — от 256 МБ **и без этого не обойтись**: сам Xray в покое занимает ~25-40 МБ, но при большой подписке (100+ серверов) и постоянных проверках через observatory его память растёт со временем — на тестах видели рост до 100-120 МБ за несколько часов аптайма. `install.sh` ставит ночной перезапуск Xray по cron именно для этого — но на роутере с 128 МБ и без swap риск нехватки памяти (и вмешательства OOM-killer ядра) всё равно реальнее, чем на 256 МБ.
- Доступ в интернет во время установки (нужно скачать Entware, xkeen, xkeen-UI, наш модуль — доступ к `bin.entware.net`, `github.com`, `raw.githubusercontent.com`).
- Рабочая **VLESS или Trojan подписка** (ссылка вида `https://.../sub/xxxxx`, отдающая base64-список серверов).

**На вашем компьютере (для одной команды установки):**
- SSH-доступ к роутеру (по умолчанию логин `root`).

## Установка

Через SSH на роутере:

```sh
sh <(wget -O - https://raw.githubusercontent.com/LackyCraft/xkeen-smartroute/main/install.sh)
```

Скрипт идемпотентен — его можно перезапускать сколько угодно раз, уже установленные компоненты он пропустит. По шагам он:

1. Проверяет, что это OpenWrt, и что хватает места.
2. Ставит Entware (если ещё не стоит).
3. Ставит `xkeen`.
4. Ставит `xkeen-UI` (порт 1000) и один раз спрашивает пароль для входа в неё.
5. Ставит наш LuCI-модуль SmartRoute + библиотеки + списки доменов.
6. Ставит `smartroute-gateway` — панель на порту 1001.
7. Настраивает cron: обновление geosite/geoip раз в 8 часов, обновление подписки — по настроенному интервалу, плюс ночной перезапуск Xray (защита от постепенного роста памяти на слабом железе).

## Что и куда устанавливается

| Путь | Что это |
|---|---|

| `/etc/nftables.d/20-xkeen-smartroute-redirect.nft` | Наша nftables-цепочка перехвата трафика (см. [Кроссплатформенность](#кроссплатформенность-как-smartroute-чинит-xkeen-на-openwrt)) — управляется через `redirect.sh`, не редактируется вручную |

| `/opt/share/xkeen-smartroute/gateway` | Бинарник панели SmartRoute (порт **1001**) |
| `/opt/share/xkeen-smartroute/panel/` | Статические файлы панели |

## Быстрый старт после установки

1. Откройте `http://<IP-роутера>/` → **Services / Сервисы → XKeen SmartRoute → Подписки**.
2. Вставьте ссылку подписки, нажмите «Импортировать» — ниже появится список серверов.
3. Перейдите на вкладку **Профили**: задайте имя (например `youtube`), выберите список доменов (категория `geosite:youtube` или свой), режим — конкретный сервер или группа с авто-выбором быстрого, отметьте сервер(а), сохраните.
4. Трафик по выбранным доменам сразу пойдёт по новому правилу — Xray перезапускается автоматически при сохранении.
5. Если сайта нет ни в geosite, ни в готовых списках — там же на странице «Профили» есть форма «Добавить свой домен(ы)»: впишите через запятую, список сразу появится в выборе.
6. На вкладке **Kill-Switch** включите жёсткую защиту для профиля (работает и для geosite, и для собственных списков).
7. Живая панель с пингом серверов, графиком трафика и логами — `http://<IP-роутера>:1001/` (SmartRoute panel).
8. Сервисные задачи (логи, ручной конфиг, апдейт ядра) — `http://<IP-роутера>:1000/` (xkeen-UI).

## Списки доменов, которых нет в geosite

Xray-core использует базу **geosite** ([v2fly/domain-list-community](https://github.com/v2fly/domain-list-community)) — сотни готовых категорий (`geosite:youtube`, `geosite:discord`, `geosite:openai`, `geosite:anthropic` и т.д.), которые SmartRoute даёт выбрать из коробки безо всякого сопровождения с нашей стороны.

Но по состоянию на 2026-08-15 в этой базе **нет** отдельных категорий для: **Character.AI**, **Grok/x.ai**, **npm registry** — для них в репозитории лежат собственные списки `lists/custom/*.lst`, которые SmartRoute тоже предлагает в выборе домен-списка (помечены как «нет в geosite»).

(Заодно проверили популярные опасения — ChatGPT/OpenAI и Claude/Anthropic **уже есть** в geosite как `openai` и `anthropic`, отдельно поддерживать их не нужно.)

Эти списки **обновляются автоматически**: workflow `.github/workflows/update-domain-lists.yml` (`scripts/update_lists.py`) раз в неделю (и по кнопке вручную, Actions → Update domain/IP lists → Run workflow) берёт кандидатов из `scripts/seeds.json`, проверяет их доступность (DNS + TLS-хендшейк, с несколькими попытками, чтобы не ловить случайные сетевые сбои) и перезаписывает `lists/custom/*.lst` только живыми доменами — если что-то отвалилось, оно само уйдёт из списка при следующем запуске, а не будет тихо простаивать годами.

Тот же прогон дополнительно сохраняет **снимки резолвленных IPv4** в `lists/ip/*.lst` — не только для трёх списков выше, но и для пары популярных сервисов (YouTube, Discord, Claude/Anthropic) просто для наглядности. Это **справочные** файлы, не маршрутизация: у CDN IP-адреса меняются постоянно, разовый DNS-снимок ничего не гарантирует — реальная маршрутизация всегда идёт по домену (geosite или наш список), а не по этим IP.

Если что-то из списков реально поменялось, пайплайн коммитит изменения и публикует **GitHub Release** с изменениями: сколько доменов/IP добавилось-убавилось по каждому сервису — см. [Releases](https://github.com/LackyCraft/xkeen-smartroute/releases).

Хотите добавить список для своего сервиса — два варианта:
- **Через PR**: добавьте кандидатов в `scripts/seeds.json`, пайплайн сам проверит и соберёт файл.
- **Прямо на роутере**: вкладка «Профили» → «Добавить свой домен(ы)» — работает без доступа к GitHub вообще, локально.

## Диагностика и типичные проблемы

```sh
sh check.sh
```

(или скачайте и запустите: `sh <(wget -O - https://raw.githubusercontent.com/LackyCraft/xkeen-smartroute/main/check.sh)`)

Скрипт проверяет: OpenWrt/Entware/xkeen/процесс xray/xkeen-UI/валидность сгенерированных конфигов/наличие ubus-бэкенда и LuCI-страниц/количество серверов и профилей — и отмечает `[OK]`/`[FAIL]`/`[--]` по каждому пункту.

| Проблема | Что проверить |
|---|---|
| После установки нет пункта меню в LuCI | `/etc/init.d/rpcd restart`, затем обновите страницу LuCI (Ctrl+F5) |
| «Импортировать» ничего не находит | Подписка должна отдавать base64-блок строк `vless://`/`trojan://` — откройте ссылку в браузере и проверьте руками |
| Профиль сохранён, но трафик не переключился | Проверьте `sh check.sh` — валиден ли `05_routing.smartroute.json`; посмотрите логи через xkeen-UI (`:1000`) |
| Не хватает места при установке Entware | Подключите USB-флешку, запустите `install.sh` заново |
| Панель на порту 1001 не открывается | Проверьте `pgrep -f smartroute-gateway`; если пусто — `/opt/etc/init.d/S98smartroute-gateway restart`, лог — `/etc/xkeen-smartroute/state/gateway.log` |
| В логе панели ошибка подключения к Xray API | gRPC API Xray слушает только `127.0.0.1:10085` и включается фрагментом `00_api.smartroute.json` — `sh check.sh` покажет, стоит ли он на месте |

## Обновление и удаление

Обновление — просто повторный запуск `install.sh` (перекачивает наши файлы поверх, xkeen/xkeen-UI обновляются своими штатными механизмами `-ux`/`-uk` и т.д.).

Удаление:

```sh
sh <(wget -O - https://raw.githubusercontent.com/LackyCraft/xkeen-smartroute/main/uninstall.sh)
# добавьте --purge, если нужно удалить и все профили/списки:
sh <(wget -O - https://raw.githubusercontent.com/LackyCraft/xkeen-smartroute/main/uninstall.sh) --purge
```

`xkeen`, `xkeen-UI` и Entware при этом не трогаются — это отдельные проекты, удаляйте их своими средствами при необходимости.
